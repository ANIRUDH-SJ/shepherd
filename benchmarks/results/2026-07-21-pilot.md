## What this pilot establishes

- All four subjects launched the same controlling-TTY worker successfully.
- The deterministic ANSI fixture reached the final Device Status Report query,
  and every terminal returned the expected response.
- cmux-linux process accounting included its seven-process Electron tree rather
  than measuring only the launcher.
- Kitty helpers and the GNOME client/server topology were included while the
  common Node benchmark worker was excluded.
- The run recorded zero subject failures and left no benchmark processes behind.
- The host-pressure check correctly downgraded the run to `pilot`.

The single measured observation shows cmux-linux with higher startup time and PSS
and lower parser throughput than the other subjects in this run. That is a useful
signal for future investigation, but the sample count and host pressure are too
poor to tell whether the differences are stable or representative.

## Methodology

- Startup boundary: subject process spawn to the prepared worker reporting ready
  from a controlling TTY.
- Memory: aggregate `/proc/<pid>/smaps_rollup` across the measured process set.
  PSS is the primary comparison because it apportions shared pages.
- Idle CPU: process CPU-tick delta over a 300 ms interval after a 500 ms settle.
- Output workload: 1,048,648-byte ANSI fixture, generated before timing.
- Completion boundary: terminal response to a final `ESC[5n` Device Status Report
  query, confirming parser consumption but not final frame presentation.
- Ordering: deterministic per-round shuffle with seed `0x6d2b79f5`.
- Timeout: 15 seconds per readiness/parser boundary.

## Limitations

1. One measured sample cannot establish variance, confidence, or p95 behavior.
2. Heavy swap usage can change startup and resource behavior unpredictably.
3. The 300 ms CPU interval is short and quantized by kernel clock ticks.
4. Parser completion is not rendered-frame throughput or input-to-photon latency.
5. No scroll, resize, multi-terminal scaling, agent-overhead, or software-rendering
   workload was measured.
6. GNOME Terminal can reuse a shared server and its existing profile, so its font
   and complete configuration were not proven identical to the isolated subjects.
7. Ghostty used a community-produced Linux AppImage rather than an official Linux
   binary, because the project did not publish one for this comparison.
8. The JSON recorded repository `HEAD` as planning commit `4356f47`, while the
   harness implementation was still uncommitted. The final merged harness includes
   later lifecycle and validation hardening, so the exact pilot source state is
   not reconstructable solely from the recorded commit.

## Requirements for a publishable rerun

- No more than 50% swap use and at least 25% memory available.
- Stable AC-power and CPU-policy conditions with low background load.
- Fixed geometry, font, and subject configuration.
- At least five warm-ups and twenty measured samples per subject.
- The final committed harness and recorded clean Git commit.
- Separate rendered-output, input-latency, scrolling, resizing, scalability, and
  GPU/software-rendering suites before making broad “fastest terminal” claims.
